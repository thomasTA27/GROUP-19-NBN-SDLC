**Overall verdict on the module: good enough to start from, not good enough as written.** The loop it describes (scope small, generate, verify every time) held up, and edge-case elicitation and self-review were worth using. What made this run safe was not in the module: a baseline, a way to review hardened tests, an independent reviewer, a route for conflicts with the inputs, a check that the controls and docs exist, and a hand-over of what was left unverified. The exit condition cannot be checked as written. The changes below add those.

### Biggest gaps in the methodology

Ordered by how much they undermine the stage.

1. **The comprehension check has no teeth.** "Explain every line without deferring to the AI" is the module's exit condition, but nothing in the workflow tests it. Asking the AI to explain the code satisfied it in form but not in substance (A1 "Loop exit"). On a multi-commit change it is also unrealistic as worded.
2. **There is no route back to Planning.** Implementation surfaced four spec conflicts, more than Design did. The module treats the spec as settled input and never mentions spec change requests, so a developer either silently picks a side or stalls.
3. **Unverified claims are not forced into tests.** Every AI claim that was probed was settled; every claim that wasn't stayed open or turned out wrong (A4 finding 1). The module's checklist asks if tests assert real behaviour, not whether the AI's factual claims were checked.
4. **The module assumes controls exist that may not.** Hooks, CI, scanners, branch protection and `CODEOWNERS` are all assumed. In this repo none of them was in effect, and nothing in the workflow makes their absence visible.
5. **Running the real thing isn't a step.** The only check that found AC18's failure was a manual smoke test against a deployed backend. The module's "verify" covers the diff and the tests only.
6. **Attribution can be undone at merge.** The module doesn't say which merge method to use, and a squash merge collapses the per-commit trailers it asks for.
7. **Cost grows fastest in this stage.** 3.3× Design's output tokens and 8.4× its cache reads, driven by one long session re-reading context.

**Gaps added by Part B** (they continue the numbering above). Each is written so it applies to any project and any coding agent. The run that found it is in B1a and B2.

8. **Corrections come in two kinds and the module counts them as one.** The module says repeated corrective iterations mean the task was scoped too large. In this run every package was small and every first output was green, yet each code package needed 1 to 3 more rounds, because review found gaps: a missing check, a risky edge case, a survivor in a mutation table. A limit meant for failed generations stopped packages that were still finding real issues.
9. **Hardened tests make the diff unreadable.** The module asks for bounded tests and defines verification as reading the diff. Once the checks asked for gap tests and mutations, tests were about three quarters of the added lines. Nothing in the module says how to review them, and the only workable answer was to review a table of mutations that the tests did or did not catch.
10. **There is no baseline step.** A dependency audit that already failed, an install script that changed files outside the project, and a tool upgrade in the middle of the run were all found by luck or by a baseline added during the run.
11. **Independent review is not in the module.** It offers a self-review prompt and calls it a first pass. In this run a reviewer that did not write the code found defects the self-review missed in five packages, and the self-review found others the reviewer missed. Neither replaces the other.
12. **Instruction files and docs have no check.** The module lists updated instruction files as an output, but nothing verifies them against the code. An audit at the end found 31 drift items, including example code that would not compile and templates with real bugs.
13. **Text and tooling hazards go unnoticed.** Invisible characters in test files, scripts that changed line endings, and a wrong count from the agent's own shell were each found by a deliberate check, never by the checklist.
14. **Unverified items have no hand-over.** 21 items were still unverified at the end (B2 row 14). The module's PR section asks for caveats, but nothing collects them while the work is done, so the list had to be rebuilt from logs.
15. **The comprehension check can be made checkable, and the module does not try.** The exit condition fails because it is a feeling. A step where the developer writes a short explanation and the agent checks it against the code turns it into something that can be run and recorded.

**Change needed in the module:**

1. **Make the exit condition checkable.** For example: before accepting, the developer writes a two-line explanation of the change in their own words, or explains the riskiest function (here, the ownership helper) without the AI. Accept that "every line" doesn't scale and say what does.
2. **Add a spec-conflict step.** When code can't satisfy two criteria at once, or a design decision is still open, raise an SCR to Planning, build to the current spec, and list the conflict in the PR caveats. Reuse Design's SCR format.
3. **Add "probe, don't assert" to the checklist.** Every factual claim the AI makes about a library, API or browser is either tested in a throwaway check or listed as unverified in the PR.
4. **Add a "controls present?" check at the start of the phase.** Confirm the hooks run, CI runs on PRs, scanners exist and `CODEOWNERS` is set. Where one is missing, say so in the PR.
5. **Add a run-it step** for changes with UI or backend behaviour: a short smoke test against a dev environment, tied to the ACs, before the PR.
6. **State the merge method:** a merge commit (or rebase merge) that keeps the signed commits; not squash.
7. **Name the Claude Code equivalents** next to the Copilot ones: plan mode for `/plan`, plain file paths for `#file:`, and `.claude/settings.json` deny rules for content exclusion.
8. **Say how to split long sessions** to control cost, and what to carry between them (the decisions log, the open SCRs).

They are written as steps and prompt samples for any project and any coding agent (GitHub Copilot, Claude Code, Codex or another).
