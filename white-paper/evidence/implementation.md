### Biggest gaps in the methodology

Ordered by how much they undermine the stage.

1. **The comprehension check has no teeth.** "Explain every line without deferring to the AI" is the module's exit condition, but nothing in the workflow tests it. Asking the AI to explain the code satisfied it in form but not in substance (A1 "Loop exit"). On a multi-commit change it is also unrealistic as worded.
2. **There is no route back to Planning.** Implementation surfaced four spec conflicts, more than Design did. The module treats the spec as settled input and never mentions spec change requests, so a developer either silently picks a side or stalls.
3. **Unverified claims are not forced into tests.** Every AI claim that was probed was settled; every claim that wasn't stayed open or turned out wrong (A4 finding 1). The module's checklist asks if tests assert real behaviour, not whether the AI's factual claims were checked.
4. **The module assumes controls exist that may not.** Hooks, CI, scanners, branch protection and `CODEOWNERS` are all assumed. In this repo none of them was in effect, and nothing in the workflow makes their absence visible.
5. **Running the real thing isn't a step.** The only check that found AC18's failure was a manual smoke test against a deployed backend. The module's "verify" covers the diff and the tests only.
6. **Attribution can be undone at merge.** The module doesn't say which merge method to use, and a squash merge collapses the per-commit trailers it asks for.
7. **Cost grows fastest in this stage.** 3.3× Design's output tokens and 8.4× its cache reads, driven by one long session re-reading context.

**Change needed in the module:**

1. **Make the exit condition checkable.** For example: before accepting, the developer writes a two-line explanation of the change in their own words, or explains the riskiest function (here, the ownership helper) without the AI. Accept that "every line" doesn't scale and say what does.
2. **Add a spec-conflict step.** When code can't satisfy two criteria at once, or a design decision is still open, raise an SCR to Planning, build to the current spec, and list the conflict in the PR caveats. Reuse Design's SCR format.
3. **Add "probe, don't assert" to the checklist.** Every factual claim the AI makes about a library, API or browser is either tested in a throwaway check or listed as unverified in the PR.
4. **Add a "controls present?" check at the start of the phase.** Confirm the hooks run, CI runs on PRs, scanners exist and `CODEOWNERS` is set. Where one is missing, say so in the PR.
5. **Add a run-it step** for changes with UI or backend behaviour: a short smoke test against a dev environment, tied to the ACs, before the PR.
6. **State the merge method:** a merge commit (or rebase merge) that keeps the signed commits; not squash.
7. **Name the Claude Code equivalents** next to the Copilot ones: plan mode for `/plan`, plain file paths for `#file:`, and `.claude/settings.json` deny rules for content exclusion.
8. **Say how to split long sessions** to control cost, and what to carry between them (the decisions log, the open SCRs).
